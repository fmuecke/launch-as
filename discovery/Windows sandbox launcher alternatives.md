# Windows sandbox launcher alternatives

Research date: 2026-10-18.

**An existing tool appears to cover the native sandbox engine: Microsoft's released `wxc-exec.exe` v1.0.1.** It accepts arbitrary Windows commands and filesystem/network policy, uses PSEC on capable hosts, preserves console I/O, and owns descendant cleanup. The next step should be an adoption test with this executable, replacing the proposed custom Rust host spike. A small wrapper and orchestration changes are still needed to connect it to `launch-as`, `wfp-lock`, `allowproxy`, and the existing restricted account. Anthropic also now publishes a standalone native Windows sandbox alpha, although its architecture differs from the agreed workflow. These conclusions come from release, package, documentation, and source inspection; **no candidate was installed or executed, and Claude compatibility or enforcement on this host has not been demonstrated**. ([Microsoft release](https://github.com/microsoft/mxc/releases/tag/v1.0.1), [executor source](https://github.com/microsoft/mxc/blob/v1.0.1/src/tools/wxc/src/main.rs), [Anthropic release](https://github.com/anthropics/sandbox-runtime/releases/tag/v0.0.80))

## The released executor already owns launch and cleanup

MXC v1.0.1, released October 17, publishes signed release binaries and is MIT licensed. Its Windows executor accepts a policy JSON file followed by `--` and the workload's executable/arguments. This is already the generic arbitrary-command launcher we proposed building. The release payload and signatures still need inspection before packaging; the published release is evidence of availability, not an independently verified local binary. ([Release](https://github.com/microsoft/mxc/releases/tag/v1.0.1), [CLI](https://github.com/microsoft/mxc/blob/v1.0.1/src/tools/wxc/src/main.rs), [license](https://github.com/microsoft/mxc/blob/v1.0.1/LICENSE.md))

The stable schema exposes `filesystem.readonlyPaths`, `filesystem.readwritePaths`, working directory, environment, timeout, and directional networking policy. The launcher serializes Windows argv, inherits the existing console when stdout/stderr are terminals, and uses parent standard handles when redirected. It creates the workload suspended, assigns it to a kill-on-close job, and resumes only after assignment succeeds. Normal foreground exit explicitly terminates remaining descendants; failure, timeout, and drop paths also own cleanup. Job draining has a bounded observation period, so acceptance must still verify that no descendants remain. **Reimplementing these mechanics would duplicate upstream code.** ([Schema](https://github.com/microsoft/mxc/blob/v1.0.1/schemas/stable/mxc-config.schema.1.0.0.json), [argument serialization](https://github.com/microsoft/mxc/blob/v1.0.1/src/mxc-sdk/src/core/mxc_common/cmdline.rs), [native runner](https://github.com/microsoft/mxc/blob/v1.0.1/src/mxc-sdk/src/backends/process_container/common/base_container_runner.rs), [job ownership](https://github.com/microsoft/mxc/blob/v1.0.1/src/mxc-sdk/src/backends/process_container/common/job_object.rs))

The intended command shape is `wxc-exec.exe policy.json -- C:\absolute\path\claude.exe --resume`. Resolve the actual `.exe`; a `.cmd` shim needs explicit command-processor handling. Environment inheritance also needs deliberate integration: `inheritDefaultEnv:true` takes profile defaults, rather than copying every variable from the invoking shell. Supply proxy and required runtime variables explicitly. ([CLI](https://github.com/microsoft/mxc/blob/v1.0.1/src/tools/wxc/src/main.rs), [environment contract](https://github.com/microsoft/mxc/blob/v1.0.1/docs/schema.md))

## PSEC-only execution depends on the complete policy

**`containment:"processcontainer"` alone does not require PSEC.** Generic requests can fall back to AppContainer/BFS/DACL paths, and `fallback.allowDaclMutation:false` only excludes DACL fallback. However, v1.0.1 rejects a request with `network.ingress.hostLoopback:"allow"` whenever its PSEC runner cannot service the complete request, before selecting fallback. That matches our mandatory localhost-listener requirement. For this pinned version, preserve that field, disable DACL mutation, and verify the guard when upgrading; there is no general `requirePsec` setting. The selected runner resolves the actual Process Security Environment APIs and attaches their security-environment handle at process creation. ([Tier-selection guard and tests](https://github.com/microsoft/mxc/blob/v1.0.1/src/mxc-sdk/src/backends/process_container/common/fallback_detector.rs), [PSEC API binding](https://github.com/microsoft/mxc/blob/v1.0.1/src/mxc-sdk/src/backends/process_container/common/secenv.rs))

Use **direct network rules**, with egress denied except numeric loopback TCP endpoints for `allowproxy`, and ingress set to `default:"deny", hostLoopback:"allow"`. This uses the released schema's CIDR/protocol/port controls while leaving web host:port decisions to the existing external proxy. Do not substitute MXC's `runtimeConfig.networkProxy`: that separate feature requires default ingress allowance and cannot combine with direct egress rules. Its documented listener limitations do not establish that the selected direct mode fails. Localhost listeners do not imply unrestricted outbound access to other localhost services. ([Networking guide](https://github.com/microsoft/mxc/blob/v1.0.1/docs/backends/process-container/networking.md), [policy serialization](https://github.com/microsoft/mxc/blob/v1.0.1/src/mxc-sdk/src/backends/process_container/common/base_container_helpers.rs), [schema](https://github.com/microsoft/mxc/blob/v1.0.1/schemas/stable/mxc-config.schema.1.0.0.json))

Actual feature availability matters more than a Windows version label. The documentation places host-loopback support at Windows 11 builds `26100.9550`/`26200.9550`; use request-aware capability checks on the intended host. `--probe` reports selection without launching the workload, but **it is not unconditionally read-only: executor startup first runs orphaned DACL-state recovery**. Evaluate it in a disposable environment before incorporating it into a host check. The intended PSEC path does not require `wxc-host-prep` or daily elevation; that privileged preparation tool serves other backend paths. ([Support progression](https://github.com/microsoft/mxc/blob/v1.0.1/docs/backends/process-container/networking.md), [probe startup path](https://github.com/microsoft/mxc/blob/v1.0.1/src/tools/wxc/src/main.rs), [host preparation](https://github.com/microsoft/mxc/blob/v1.0.1/docs/backends/process-container/host-prep.md))

## Alternatives change the selected boundary or environment

The closest candidates are credible tools, but none found is a better match for the agreed same-account, native-host, mandatory-PSEC workflow.

The statement that Anthropic has no Windows sandbox now needs qualification. Its standalone package ships a Windows backend, while Claude Code's product documentation still describes shell sandboxing for macOS/Linux/WSL2, with native Windows commands unsandboxed. Standalone availability does not establish native Claude integration. Anthropic's Windows WFP source filters outbound connect layers, so it also does not establish the required remote-inbound denial. Its piped/no-window launch path needs separate TUI testing. ([Claude sandbox documentation](https://code.claude.com/docs/en/sandboxing), [published package](https://registry.npmjs.org/@anthropic-ai/sandbox-runtime/-/sandbox-runtime-0.0.80.tgz), [WFP implementation](https://github.com/anthropics/sandbox-runtime/blob/v0.0.80/vendor/srt-win-src/src/wfp.rs), [launch implementation](https://github.com/anthropics/sandbox-runtime/blob/v0.0.80/vendor/srt-win-src/src/launch.rs))

## Build the integration after testing the executor

Keep the existing responsibility split: `launch-as` enters the account, `wfp-lock` supplies its outer egress fence, and owner-run `allowproxy` applies the shared web allowlist. Let `agent-win-sandbox` pin/package the executor and generate its policy. A small wrapper should resolve the current account profile and project, add exact read-only runtime roots, snapshot configuration, verify applied proxy policy, supply environment/argv, and return the workload exit code. User-editable configuration retains the agreed consequence: Claude can change future-run policy within its writable reach. MXC does not implement this project's cross-component policy contract. Its schema and CLI are sufficient primitives to compose it. ([Schema](https://github.com/microsoft/mxc/blob/v1.0.1/schemas/stable/mxc-config.schema.1.0.0.json), [CLI](https://github.com/microsoft/mxc/blob/v1.0.1/src/tools/wxc/src/main.rs))

The first gate is a disposable supported Windows guest, followed by an unelevated run in the actual restricted-account workflow. Verify existing project/profile contents and alternate-path denials; proxy-only egress and controlled DNS evidence; localhost success versus controlled LAN-peer failure for IPv4, IPv6, and wildcard listeners; Claude authentication, resume, PowerShell, Git, builds, and local MCP servers; and Ctrl+C, resize, root exit, abrupt launcher death, and nested jobs under `launch-as`. **Source review does not establish inbound enforcement or Claude interactivity.** Only add native host code for a concrete gap these tests expose.

## Conclusion

The implementation decision should move from developing a PSEC launcher to qualifying and composing Microsoft's released executor. This also creates a useful stopping point: if the direct-loopback policy fails on the supported host, first determine whether the missing behavior is an OS/MXC issue before creating a second launcher over the same primitive. Keep the original plan as the requirements record and revise its implementation milestone only after the adoption test establishes what local code is necessary.
